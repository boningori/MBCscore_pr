# 1. 2つのタブで同じ試合を記録できてしまう

## 背景

同じ端末で同じ試合を2つのタブから記録すると、**あとから書いたほうが勝ち、もう片方の記録が黙って消える**。

実測（Playwright・本番ビルド・同一 context の2ページ）:

```
1) tab1 で2点        -> 保存 {points:2, scores:1}
2) tab2 を開く       -> 画面 2（正しく読めている）
3) tab2 で2点        -> 保存 {points:4, scores:2}
4) tab1 でさらに2点  -> 画面 4、保存 {points:4, scores:2}   ← tab2 の1本が消えた
5) 開き直す          -> 4（本来は 6）
```

3本記録して2本しか残らない。原因は `useGameAutoSave` が**メモリ上の状態を丸ごと書く**ことにある。`tab1` は `tab2` の得点を知らないまま自分の版で上書きする。

たちが悪いのは、**両方のタブが同じ「4」を表示し、どこにも異常が出ない**ことである。スコアシートとしても辻褄が合い、1本足りないことに気づく手がかりが無い。

他タブを知る仕組みは一切ない。

```
$ grep -rn "'storage'|BroadcastChannel|navigator.locks|SharedWorker" src/ --include=*.ts --include=*.tsx | grep -v test | wc -l
0
```

PWA を入れたうえでブラウザでも開く、ブックマークを二度叩く、といった経路で普通に起こり得る。

## 決めたこと

**後から開いたタブに記録させない。** 起きてから警告するのではなく、起きないようにする。

記録中のタブが「自分が使っている」印を定期的に書き、別のタブはその印が新しいあいだ試合画面へ入れない。

**逃げ道（それでも再開する）は用意しない。** 用意すると、いま直そうとしている事故を利用者が自分で起こせる道を残すことになる。タブを閉じれば心拍が止まり、時間切れで自動的に開く。

## 仕組み

`src/utils/sessionOwner.ts` を新設する。

```ts
/** 記録中のタブを表す印の置き場 */
const OWNER_KEY = 'minibasket-session-owner';

/** 心拍の間隔 */
export const HEARTBEAT_MS = 5_000;

/** これを過ぎた印は「もう誰も使っていない」とみなす */
export const OWNER_STALE_MS = 30_000;

/** このタブのid（読み込みごとに1つ） */
export function myTabId(): string;

/** 自分が使っていると宣言する（心拍） */
export function claimSessionOwner(): void;

/** 自分が持っているなら手放す */
export function releaseSessionOwner(): void;

/** 別のタブが、いま記録中か */
export function isOwnedByOtherTab(): boolean;
```

印は `{ id, at }`。`isOwnedByOtherTab()` は次の順で偽を返す——印が無い／自分の id ／`Date.now() - at > OWNER_STALE_MS`。

**心拍が要る理由**: 自動保存は状態が変わったときにしか走らない。タイムアウトやハーフタイムで数分間タップが無いと印が古くなり、その隙に別のタブが入れてしまう。だから状態と無関係に一定間隔で打つ。

**30秒にする理由**: 心拍が5秒なので、通信も何も無いこの仕組みでは 6 回落とすまで猶予がある。短すぎると静かな時間に所有権を落とし、長すぎると端末が落ちたあとの復帰が遅れる。

## どこで塞ぐか

ホームの **「試合を再開」と「新規試合開始」の両方**。

再開だけを塞いでも足りない。別のタブが記録中に新規試合を始めると、同じセッションのキーをその新しい試合で上書きすることになり、結果は同じである。

塞いだときはトーストで知らせる。

> 別のタブでこの試合を記録中です。そちらのタブで続けてください。

ボタンを無効化する形にはしない。所有権は他のタブの都合で変わるのに、ホームは描画のたびにしか読み直さないため、見た目と実態がずれる。押した瞬間に判定して断るほうが確かである。

## やらないこと

- **`useGameAutoSave` には手を入れない。** 書き込みを止める方向で守ると、「記録しているのに保存されないタブ」ができる。入口で塞ぐほうが分かりやすい
- **記録中のタブ側には何も出さない。** そちらは正常に動いている
- **`storage` イベントは使わない。** 印を読むだけで足りる

## テスト

`src/utils/sessionOwner.test.ts`（新規）

- 印が無ければ `isOwnedByOtherTab()` は偽
- 自分が `claim` した直後は偽（自分の印だから）
- 別の id の新しい印があれば真
- 別の id でも 30 秒より古ければ偽
- `release` すると偽に戻る
- 壊れた印（JSONとして読めない）は偽（塞がない側へ倒す）

`src/App.sessionOwner.test.tsx`（新規）

- 別のタブの新しい印があるとき、「試合を再開」を押しても試合画面へ進まず、トーストが出る
- 同じく「新規試合開始」も進まない
- 印が古ければ、いつもどおり進む

`e2e/twoTabs.spec.ts`（新規）

この事故は2つのタブが同じ localStorage を共有することで起きる。jsdom では再現できない。実測に使った手順（同一 context の2ページ）をそのまま固定する。

# 2. バックアップの version が比較されていない

## 背景

書き出しは `BACKUP_VERSION = '2.0'` を入れるが、取り込みは**存在を確かめるだけ**で値を一度も見ない（`dataBackup.ts:794`）。

```ts
if (!data.version) { return { type: 'unknown', ... }; }   // 以降、値は読まない
```

今日の実害はゼロである。直す理由は一点だけで、**次に形式を変えたとき、既に配られているアプリが新しいファイルを拒めるようにしておく**ため。あとから足しても、その時点で世に出ている版には効かない。

`registerType: 'prompt'` なので、更新を断り続けた古いアプリは長く残る。

## 決めたこと

**メジャーが自分より新しいファイルは受け付けない。**

> このバックアップは新しいバージョンのアプリで作られています（v3.0）。アプリを更新してから取り込んでください。

1.x と 2.x は**いままでどおり読む**。`e590901` が 1.x を作り、`e6b064c` がフィールドを足して 2.0 にした——追加だけの変更だったので、古いファイルはいまも読める。その互換性は壊さない。

**メジャーを読み取れないファイルも、いままでどおり受け付ける。** 断る条件を「はっきり新しいと分かるもの」だけに絞り、想定外の形で既存の取り込みを壊さない。

## テスト

`src/utils/dataBackup.version.test.ts`（新規）

- `'1.0'` は受け付ける（古い形式の互換を壊さない）
- `'2.0'` / `'2.5'` は受け付ける
- `'3.0'` は断り、案内文にファイルの版が入る
- `'10.0'` も断る（文字列比較ではなく数として見る）
- `version` が無ければ、いままでどおり「MBCscoreのエクスポートデータではない」
- `'abc'` のように読めない版は、いままでどおり受け付ける
