# 6個目以降のファウルの取りこぼし防止 — 設計

- 日付: 2026-08-18
- ステータス: 設計承認済み（実装計画待ち）

## 背景・目的

公式様式のファウル欄は選手1人につき5枠しかない。一方でアプリは6個目以降のファウルを止めずに記録する。結果として、`player.fouls` には6個目が入るのに `RunningScoresheet` は `[0,1,2,3,4]` の5マスしか描かず、**6個目以降が無言で様式から消える**。

チームパネルとチーム統計は `F6` と出すため、画面と出力が食い違う。記録者には取りこぼしに気づく手がかりが無い。

6個目が発生する原因は2通りあり、望ましい応答が逆になる。

| 原因 | 実際に起きること |
|---|---|
| 選手の押し間違い（本来は別の選手） | 誤記録。止められるべき |
| 練習試合で失格者が続行 | 実在するファウル。記録されるべき |

このアプリは「練習試合では相手チームの同意のうえで退場者が出続ける運用がある」ため出場を止めない方針を明文化している（`src/hooks/useFoulOutNotice.ts`、`src/context/GameContext.tsx`）。したがって一律ブロックは採らず、**確認を挟んで記録者に判断を委ねる**。

## スコープ

### やること

- ファウル記録時、6個目以降になる場合に確認ダイアログを出す（押し切れば記録）
- ファウルの選手付け替えで6個目を作る場合に、編集モーダル内へインライン警告を出す
- ベンチテクニカル（交代要員）の経路にも、現在のファウル数を渡して確認の対象に含める

### やらないこと（YAGNI・今回のスコープ外）

- **`RunningScoresheet` の変更**（様式・PDF/JPEG出力の見た目は一切変えない）。ユーザーの明示的な制約
- **reducer の変更**。押し切ったときは従来どおり記録され、チームファウルにも加算される
- 既に保存済みの試合に残る取りこぼしの遡及表示
- 6個目をブロックする、チームファウルだけ計上する等の代替案（検討のうえ不採用。「設計判断」参照）

## 設計判断（ユーザー合意事項）

| 論点 | 決定 |
|---|---|
| 様式（5枠）の変更 | しない |
| 6個目の扱い | 確認を挟み、押し切れば記録する（ハードブロックはしない） |
| チームファウルへの加算 | 従来どおり加算する（ペナルティ判定を正しく保つため） |
| 付け替え経路 | 対象に含める。ただしダイアログではなくインライン警告 |

### 不採用にした案

- **完全ブロック** — 練習試合で実在するファウルとチームファウルが記録から落ち、以降のペナルティ判定（5個目からFT）が実際より軽くなる。出場を止めない方針とも矛盾する。
- **選手には付けずチームファウルだけ計上** — ペナルティ判定は保てるが、「誰のファウルか分からない記録」という新しい状態を増やす。保留アクション（`playerId: 'unknown'`）と紛らわしく、割に合わない。

## 判定条件

**確認を出すのは「現在のファウル数が5以上」のときだけ**。つまり、これから記録する分が6個目以降になる場合。

既存の `isFouledOut`（`getDisqualification(fouls) !== null || currentFoulCount >= MAX_PERSONAL_FOULS`）を流用してはいけない。失格は D 1つ・T/U 2回でも成立し、どちらも5個目より先に来る。それを条件にすると、**まだ様式に収まる3個目・4個目にまで確認が出て**、本来止めたい場面の重みが薄れる。

```
確認を出す:  fouls.length >= MAX_PERSONAL_FOULS  (= 5)
```

| 現在のファウル数 | 記録される分 | 様式 | 確認 |
|---|---|---|---|
| 3（うちD 1つで失格済み） | 4個目 | 収まる | 出さない |
| 4 | 5個目 | 収まる | 出さない |
| 5 | 6個目 | **収まらない** | 出す |
| 6 | 7個目 | **収まらない** | 出す |

## ゲート1: 記録時の確認（FoulInputFlow）

### 置き場所

`src/components/FoulInputFlow/FoulInputFlow.tsx` に置く。選手のファウルを記録する入り口は複数あるが（通常の記録・保留アクションの解決・保留の直接解決）、**いずれもこのコンポーネントの `foulType` ステップを通る**ため、ここに1つ置けば取りこぼさない。呼び出し側それぞれに足すと必ずどれかが漏れる（`useFoulOutNotice` が状態の差分で見ているのと同じ理由）。

例外は交代要員のテクニカルだけで、これは `foulType` ステップを通らない（ゲート1bで扱う）。

### タイミング

ファウル種類を選んだ直後、後続ステップへ進む前。

シューター選択やFT結果まで入力させてから止めると、入れた分が無駄になる。逆に種類を選ぶ前に出すと、まだ何を記録するか決まっていない段階で警告することになる。

対象となる分岐:

- P 通常タップ（`handlePFoulNormalTap`）— ペナルティ有無にかかわらず
- P 長押し／Shift+Enter（`handlePFoulLongPress`）
- T・U・D（`handleSpecialFoulSelect`）

### 文言

```
このファウルは6個目です

#4 選手A は既に5ファウルです。
6個目以降は公式様式のファウル欄（5枠）に記録できません。
チームファウルには加算されます。

[記録する]  [やめる]
```

- 既定フォーカスは「やめる」（`data-autofocus`）。誤タップで開いた確認をEnterで押し切らせない。既存の確認ダイアログと同じ作法
- 「様式に記録できない」ことと「チームファウルには入る」ことの両方を書く。片方だけだと、記録者が「では記録しない方がよいのか」を判断できない

### 実装メモ

- 共通の `ConfirmModal`（`src/components/Modal`）を使う。`FoulInputFlow` 自身が `Modal` の上に載るが、`modalStack` は LIFO なので端末の戻る操作は確認ダイアログから先に閉じる
- 確認待ちの間、どの分岐へ進むはずだったかを state で保持する。関数を state に入れると React が更新関数と解釈するため、種別（`FoulType`）と分岐の種類を持つ素のオブジェクトにする

## ゲート1b: 交代要員のテクニカル（App.tsx）

ベンチファウルの入力は `benchFoulMode` で `shooter` ステップから始まり、`foulType` ステップを通らない。そのためゲート1では捕まらない。

交代要員（Sub）だけは選手行に「T」を書くので、その選手が既に5ファウルなら同じ取りこぼしが起きる。コーチ・A.コーチ・ベンチ関係者は選手行に書かないため対象外。

判定は `handleBenchPlayerSelect`（`src/App.tsx`）に置く。ベンチ選手を選んだ直後で、FT結果を入力する前。ゲート1と同じ「決めた直後・詳細を入れる前」に当たる。

- 条件・文言・ボタンはゲート1と同じ
- 「やめる」を選んだら選手選択ステップに留まる（`coachFoulState.step === 'selectPlayer'` のまま）

なお、ベンチ選手一覧には現在のファウル数が既に `F:{n}` として出ている（`src/App.tsx` の交代要員選択モーダル）。確認はその上での最終ガード。

## ゲート2: 付け替え時の警告（EditActionModal）

ゲート1だけでは穴が残る。**ファウルの選手を付け替えると、確認を通らずに6個目を作れる** — `handleEditFoul`（`src/context/reducers/foulHandlers.ts`）は付け替え先のファウル数を見ていない。

`src/components/EditActionModal/EditActionModal.tsx` に、既存の `conversion-notice` と同じ見せ方でインライン警告を出す。

- 条件: 編集対象がファウルで、選択中の付け替え先が**現在5個以上**のファウルを持つ（付け替え元と別人のとき）
- 文言: 「⚠️ #5 選手B は既に5ファウルです。付け替えると6個目になり、公式様式には記録されません」
- **保存はブロックしない**。付け替えは長押し→編集と既に慎重な操作で、ダイアログを重ねるのは過剰

`EditActionModalProps.players` は `Player[]` を受け取っており `fouls` を持つため、追加の受け渡しは不要。

## 変えないもの

- `RunningScoresheet`（様式・PDF/JPEG出力）
- reducer 全般（`handleAddFoul` / `handleAddFoulWithFreeThrows` / 保留解決 / `handleEditFoul`）
- 既に保存済みの試合データ

## テスト

### FoulInputFlow

- 4ファウルの選手にPを記録 → 確認は出ず、そのまま `onComplete`
- 5ファウルの選手にPを記録 → 確認が出て、`onComplete` はまだ呼ばれない
- 確認で「記録する」 → `onComplete` が呼ばれる
- 確認で「やめる」 → `onComplete` は呼ばれず、種類選択に留まる
- D 1つで失格済みだが3ファウルの選手 → 確認は出さない（様式に収まるため）
- T・U・D、およびPの長押し（シュートファウル）でも同じ境界で確認が出る

### 交代要員のテクニカル

- 5ファウル以上のベンチ選手を選ぶ → 確認が出る
- 4ファウル以下のベンチ選手を選ぶ → 確認は出ず、FT入力へ進む

### EditActionModal

- 付け替え先が5ファウル以上 → 警告が出る／保存ボタンは押せる
- 付け替え先が4ファウル以下 → 警告は出ない
- 付け替え先が元と同じ選手 → 警告は出ない
