# 割れた選手カードの手動統合 — 設計

- 日付: 2026-08-19
- ステータス: 実装済み

## 背景・目的

選手スタッツ分析の識別キーは `氏名` + `ライセンスNo.`（`generatePlayerKey`）。この2つは名簿の編集で動くため、変える前に記録した試合が別人のカードとして残る。

v1.3.6 で `buildIdentityAliases` を入れ、**氏名を手掛かりに名簿を引いて**ライセンスNo.の入力・訂正・削除を吸収した。しかし手掛かりが氏名である以上、**氏名が動くケースは原理的に1つも救えない**。実測（2026-08-19、`aggregatePlayerStats`）:

| 記録に残っている氏名 | 名簿の氏名 | 結果 |
|---|---|---|
| `佐藤　太郎`（全角スペース） / `佐藤 太郎` | `佐藤 太郎` | 2枚に割れる |
| `佐藤太郎`（スペース無し） / `佐藤 太郎` | `佐藤 太郎` | 2枚に割れる |
| `斉藤 太郎`（誤字） / `齋藤 太郎` | `齋藤 太郎` | 2枚に割れる |
| `タロウ`（コートネーム） / `佐藤 太郎` | `佐藤 太郎` | 2枚に割れる |

全角・半角スペースの混在は日本語入力では日常的に起きる。名簿を打ち直した年に必ず出る種類のもの。

割れたカードはどちらも通算・平均・成長グラフが実態と食い違う。

### 設計原則としての位置づけ

このコードベースには一貫した判断がある —— 「別人を1人に混ぜるより、同一人物が割れるほうがまだ直しやすい」（`buildNumberAliases` / `buildIdentityAliases`）。自動判定は曖昧なら寄せない、という安全側の設計になっている。

ところが**現状その「直しやすい」が成立していない**。割れたとき利用者に打つ手が無い。本機能は原則の後半を初めて成立させるもので、「安全側に倒した自動判定 + 人が直せる出口」で完結させる。

## スコープ

### やること

- 分析画面で、割れた選手カードを利用者が統合できるようにする
- 統合は**集計時の名寄せ**として持つ。試合記録は一切書き換えない
- 統合の解除ができる
- 割れていそうな組を検知して一覧で知らせる（提案のみ）
- 統合設定をバックアップの往復対象に含める

### やらないこと（YAGNI・今回のスコープ外）

- **自動での統合**。検知は提案までで、確認なしに寄せることはしない
- **試合記録そのものの書き換え**。`GameRecord` は読み取り専用のまま
- **チームをまたいだ統合**。非表示選手と同じくマイチームごと
- **候補の検知に背番号の一致を使うこと**。ミニバスは6年生が抜けたあと下級生が番号を引き継ぐため、別人が同じ番号で毎年候補に出る。誤検知が邪魔になるほうが大きい（ユーザー判断）
- **統合したときに名簿の訂正を促すヒント**。次から自動で寄るようになる利点はあるが、機能が増えるので入れない（ユーザー判断）
- 統合を相手チームの選手へ適用すること（分析対象はマイチームのみ）

## 設計判断（ユーザー合意事項）

| 論点 | 決定 |
|---|---|
| 直し方 | 手動で統合（表示側の名寄せ）。記録は書き換えない |
| 入口 | 候補を検知して知らせる ＋ 手動でも選べる |
| 統合後の代表（氏名・背番号） | 名簿に載っている側を使う |
| 候補の検知に背番号を使うか | 使わない |
| 名簿の訂正を促すか | 促さない |

## データ設計

### ストレージ

新規キー `minibasket-merged-players`。非表示選手（`minibasket-hidden-players`）と同じ作法にそろえる。

```ts
// チームID → { 記録上のキー: 代表キー }
type MergedPlayers = Record<string, Record<string, string>>;
```

- `createJsonStorage` で読み込み時に型を検証する。配列や `null` が入っているとチームIDでの索引が壊れるため、素のオブジェクトのみ受ける（`hiddenStorage` と同じ判定）
- 接頭辞が `minibasket-` なので端末内ミラーバックアップ（`mirrorBackup`）は自動で対象になる
- JSONバックアップ（`dataBackup`）には項目を追加して往復させる。`hiddenPlayers` と同じマージ方針

### 対応表は常に平坦に保つ

`A → B` と `B → C` が同時に存在すると解決が連鎖し、循環も作れてしまう。**保存する対応表は深さ1に保つ**。

統合を実行するとき:

1. 代表キーが既に別の代表へ寄っていれば、その終端を代表とする
2. 既存の対応表のうち、今回まとめるキーを指している項目を新しい代表へ張り替える
3. まとめるキーそれぞれから代表への項目を書く（代表自身は書かない）

これで値として現れるキーが対応表のキーになることはなく、解決は1回の参照で済む。

### 代表キーの決め方

統合を実行する時点で決める（集計側は決まった代表キーを使うだけ）。

優先度は3段。代表の氏名がそのままカードに出るので、名簿どおりの表記になってほしい。

1. 名簿と**表記まで一致する**カード
2. **空白を無視すれば**名簿に一致するカード
3. 名簿に無いカード（コートネームや誤字）

同じ優先度どうしは、記録がいちばん新しいカード。

空白を無視した一致だけで判定すると、全角スペースと半角スペースのカードが
どちらも名簿に一致してしまい、肝心の「どちらの表記を残すか」を決められない。

名簿は「いま正しい情報」なので、既存の番号の寄せ方（`buildNumberAliases` がユニフォーム番号を代表にする）と同じ考え方。

## 集計への効かせ方

`aggregatePlayerStats` のキー決定は現在3段:

1. `buildIdentityAliases` — ライセンスNo.の揺れを名簿で吸収
2. `collectCollidingKeys` — 同姓の衝突を期間で絞る前の全試合で判定
3. `buildPlayerKeys` — 衝突したら代表番号を足す

ここに**手動の統合を最後の上書きとして足す**。

```
最終キー = 手動の対応表[buildPlayerKeys の結果] ?? buildPlayerKeys の結果
```

- 手動が常に勝つ。自動判定は名簿からの推論にすぎず、人が「同じ人だ」と言ったらそれが正しい
- 対応表のキーは **利用者がカードで見たキー**（＝`buildPlayerKeys` の出力。`#背番号` の接尾辞が付いていればそれを含む）。見えているものを統合する、という対応にする
- 対応表は静的な引き当てで、期間にも試合の絞り込みにも依存しない。期間を変えても統合は外れない
- 統合は記録を書き換えないので、`collectCollidingKeys` が見る衝突の有無は統合の前後で変わらない。したがって `#背番号` 付きのキーが統合によって別のキーへ変わり、対応表が宙に浮くことはない

### 代表の氏名・背番号

集計後の `name` / `number` は、**代表キーに属する記録のうちいちばん新しい試合のもの**を使う。代表キーの記録が1件も無い場合（対応表だけが残っている）は、従来どおりその組でいちばん新しい試合のものにフォールバックする。

## 候補の検知

### 判定

一覧に出ているカードを、**空白（半角・全角）をすべて取り除いた氏名**で束ねる。2枚以上になった束を候補として提案する。

### 候補から除く

**名簿に同じ（正規化後の）氏名の選手が2人以上いる場合、その氏名の束は候補にしない。** 名簿で意図的に分けている2人（別々のライセンスNo.を割り当てている等）を「割れている」と誤って案内しないため。`buildIdentityAliases` が寄せない条件と同じ判断にそろえる。

### 表示

- 一覧の先頭に「同じ選手が分かれているかもしれません（N組）」を出す
- 押すと候補の組が並び、1組ずつ確認して統合する
- **提案するだけで、確認なしには統合しない**
- 検知が拾えない組（コートネームと氏名など、文字列がまったく違う場合）は手動選択で統合する

## 操作

| 操作 | 導線 |
|---|---|
| 手動で統合 | 一覧の「統合」ボタン → 選択モード → 2枚以上選ぶ → 確認 → 統合 |
| 候補から統合 | 一覧先頭の案内 → 候補の組を確認 → 統合 |
| 統合の確認 | まとめる枚数・代表になる氏名と背番号・合算後の試合数を出す |
| 統合済みの表示 | カードに「統合済み」の印（件数は保持しない） |
| 統合の解除 | 統合済みカードの詳細から「統合を解除」 |

解除は対応表から該当項目を消すだけ。試合記録は無傷なので元の枚数に戻る。

## 非表示選手との関係

統合すると `playerKey` が変わるため、元のキーに付いていた非表示設定はそのままでは外れる。

- **統合**: まとめる組のどれかが非表示なら、代表キーを非表示にし、組の元のキーの設定は消す。統合したら選手が復活した、と見えないようにする
- **解除**: 代表キーの非表示設定はそのまま残す。組の他のキーは表示に戻る

## エラー・異常系

| 状況 | 挙動 |
|---|---|
| 対応表に、記録に存在しないキーが残っている | 無視する（統合済みの選手の記録を全部削除した場合など）。解決は「引けなければ元のキー」 |
| 対応表が壊れた形（配列・null・値が文字列でない） | `createJsonStorage` の検証で捨て、統合なしとして扱う |
| 統合しようとした組が1枚以下 | 統合を実行しない（ボタンを押せない） |
| 代表キーが自分自身を指す項目 | 書かない。書かれていても解決で無視する |
| マイチームを削除した | そのチームIDの項目は残るが参照されない。非表示選手と同じ扱い |

## テスト

### 純粋関数

**対応表（`mergedPlayers`）**
- 統合すると、まとめたキーが代表を指す
- 代表が既に別の代表へ寄っていれば終端へ張り替える（連鎖を作らない）
- 既存項目のうち、今回まとめるキーを指しているものを新しい代表へ張り替える
- 解除で該当項目だけが消え、他の統合は残る
- 記録に存在しないキーが混ざっても解決が壊れない

**代表キーの決定**
- 名簿に一致するカードが代表になる
- 名簿に一致が複数あれば、記録がいちばん新しいほう
- どれも名簿に無ければ、記録がいちばん新しいほう

**候補の検知**
- 全角・半角スペースの違いだけの氏名を1組として拾う
- スペース無しの表記も同じ組に入る
- 名簿に同じ氏名が2人いる場合は候補にしない
- 1枚しかない氏名は候補にしない

### 集計（`aggregatePlayerStats`）

- 統合すると1枚になり、通算・平均・出場Q・ファウル・試合別履歴が合算される
- 成長グラフのもとになる `gameHistory` が日付順に並んだまま合算される
- 手動の統合が `buildIdentityAliases` の結果より優先される
- 解除すると元の枚数に戻り、各カードの数値が統合前と一致する
- 期間で絞っても統合が外れない

### バックアップ

- エクスポート → 全消去 → インポートで統合設定が復元される
- 端末側とバックアップ側の統合設定がマージされる（`hiddenPlayers` と同じ方針）
- 統合設定を持たない旧バックアップを取り込んでも壊れない

### UI

- 選択モードで2枚以上選ぶまで統合ボタンが押せない
- 確認に、代表になる氏名・背番号と合算後の試合数が出る
- 候補の案内は該当が無ければ出ない
- 統合済みカードに印が出る
- 詳細から解除できる
- 非表示だったカードを含む組を統合すると、代表が非表示のままになる

## 残る限界

- **同姓同名・ライセンスNo.未入力・同じ背番号**で記録された2人は、記録に区別する材料が無いため分離できない。統合機能があってもなくても変わらない
- 統合は分析画面の見え方だけを変える。試合履歴・公式様式の表示は記録どおりのまま
