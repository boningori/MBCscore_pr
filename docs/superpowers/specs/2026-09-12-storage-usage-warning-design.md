# 保存領域の残量をホームでも知らせる — 設計

- 日付: 2026-09-12
- ステータス: 設計承認済み（2026-09-12）／**前提の誤りを受けて改訂（2026-09-12）**
- 対象: `src/components/Home/StorageWarning.tsx`（新設）, `src/components/Home/Home.tsx`, `public/manual.html`

## この設計書の改訂について

初版は「容量が近いことの警告が無い」という前提で書かれていた。**これは誤りである。**

`src/utils/storageUsage.ts` は 2026-08-06（`eaafdd8`）から存在し、設定画面 → データ管理 に使用容量バーと、8割超の警告文を既に出している。

```
端末内の使用容量        4.2MB / 約5.0MB
[████████████░░░]
⚠️ 空きが少なくなっています。バックアップを保存し、試合履歴から古い試合を削除してください。
```

計測（`estimateStorageUsage`）・しきい値（`WARN_RATIO = 0.8`）・表示の整形（`formatBytes`）はすべて揃っている。初版が設計していた計測モジュールは**作らない**。

残っている穴は**設定画面の奥にしか無いこと**である。データ管理の欄は折り畳みの中にあり、普段そこを開く用事は「バックアップを取る」ときだけで、まさにその用事を思いつかない人に届かない。この設計書はそこだけを埋める。

## 背景

このアプリは全データを端末内に置く。試合履歴は試合を録るたびに増える。実測は `dataBackup.ts:483` に残っている。

> 実測（記録150件・12人×2チーム・日本語名の1試合）:
>   localStorage 上   52.9KB / 試合
>   localStorage 5MB の上限に達するのは約95〜99試合

週末に2試合、年30試合なら3シーズン強で到達する。

到達したときの手当ては既にある。試合終了時の履歴保存は成否を見て分岐し、失敗すれば「端末の空き容量が足りない可能性があります」を出してセッションを消さない。記録は失われない。

8割を超えたことの知らせも既にある。ただし**設定画面を開いた人にしか見えない**。開かないまま録り続けた人が最初に知るのは、試合が終わって保存を押したその瞬間になる。体育館で撤収しながらバックアップを書き出して古い試合を選んで消す、というのは無理がある。

## スコープ

### やること

- 8割を超えているあいだ、ホームに帯を出す
- 説明書に、その帯が出たときの片付け方を書く

### やらないこと（YAGNI・今回のスコープ外）

- **計測を作り直さない。** `estimateStorageUsage` / `WARN_RATIO` / `formatBytes` をそのまま使う
- **設定画面の表示は触らない。** あちらは「見に行けば分かる」ためのもので、今回足すのは「見に行かなくても届く」ためのもの。両方要る
- **新しい削除手段を作らない。** 履歴の1件削除と全体バックアップの書き出しが既にある
- **自動削除は一切しない。** 記録アプリが黙って記録を捨てることは無い
- **段階を分けない。** しきい値は既存の `WARN_RATIO`（8割）ひとつ

## 既存の計測に従う点

初版の設計と既存実装が食い違っていた2点は、**既存に合わせる**。

1. **数えるのはアプリのキーだけ**（`minibasket-` / `mbc_` / `mbc-`）。初版は「オリジン全体を数える」としていたが、既存は `mirrorBackup.ts` のバックアップ対象と同じ基準で揃えてあり、揃っていることを `mirrorBackup.prefix.test.ts` が見張っている。片方だけ広げると、その約束が崩れる
2. **判定は `ratio > WARN_RATIO`**（ちょうど8割では出さない）。比率は 1 で頭打ち。初版は `>=` としていたが、揃っていないほうが害になる

`navigator.storage.estimate()` を使わない理由は既存モジュールの冒頭コメントが既に書いている。

## 表示

`src/components/Home/StorageWarning.tsx` を新設し、`Home` の `InstallPrompt` の直前（メニューの下）に置く。カードの作りは `InstallPrompt.css` に揃え、縁だけ警告色にする。

```
⚠️ 保存領域の空きが少なくなっています
端末内の使用容量は 4.2MB / 約5.0MB です。いっぱいになると、新しい試合を保存できなくなります。
設定 →「データ管理」からバックアップを保存し、試合履歴から古い試合を削除してください。
```

言い回しは設定画面の警告文（「バックアップを保存し、試合履歴から古い試合を削除してください」）をそのまま引き継ぐ。同じことを別の言葉で二度言うと、別のことのように読める。

**閉じるボタンは付けない。** `InstallPrompt` は閉じられる（`minibasket-install-guide-dismissed` に残る）が、あれは無くても困らない案内である。こちらは放置すると記録が保存できなくなるので、8割を切るまで出続ける。消したければ実際にデータを減らせばよい。

**ボタンも付けない。** 「設定」も「試合履歴」もすぐ下のメニューに並んでいる。帯から重ねて出す必要はなく、「押せるものだけが角丸の箱」という既存の方針にもそのまま乗る。帯は情報表示であって、操作ではない。

**「あと何試合」は書かない。** そこだけ 52.9KB/試合 という推定値を混ぜると、人数の少ないチームや記録の薄い試合では平気で倍ずれる。外れる数字を書くくらいなら書かない。

## 計測のタイミング

`Home` の既存方針どおり、**描画のたびに測る**。

`Home.tsx:25` は `loadMyTeams` と `getGameSessionState` について既にこう決めている。

> 描画のたびに読み直す。（中略）どちらも小さなJSONの読み出しで、ホームの再描画はまれ。

`estimateStorageUsage` は数MBの文字列を実体化するので、あの2つより重い。それでもマウント時1回に絞らないのは、設定モーダルからバックアップを復元してもホームは再マウントされないためである（同じコメントがその理由を書いている）。復元でデータが増えたのに帯が出ない、という食い違いをここで作りたくない。

設定画面側は `useState` + モーダルを開いたときの再測という別の作りだが、あちらは開閉のたびに必ず測り直されるので同じ穴は無い。

## テスト

`src/components/Home/Home.storageWarning.test.tsx` を新設する。

- 8割ちょうどでは帯が出ない（既存の判定が `>` であることに合わせる）
- 8割を超えると帯が出て、使用量が読める（`4.2MB / 約5.0MB`）
- 帯に閉じるボタンが無い
- 帯が出ていても、メニュー（新規試合開始・試合履歴）はいつもどおり押せる

しきい値を跨がせるには、`estimateStorageUsage` を差し替えるのではなく **実際に localStorage を太らせる**。測る対象が localStorage そのものなので、そこを模してしまうと何も確かめたことにならない。既存の `storageUsage.test.ts` も同じやり方を採っている。

`src/utils/storageUsage.test.ts` は既にあり、変更しない。
