# 保存領域の残量を先に知らせる — 設計

- 日付: 2026-09-12
- ステータス: 設計承認済み（2026-09-12）
- 対象: `src/utils/storageUsage.ts`（新設）, `src/components/Home/StorageWarning.tsx`（新設）, `src/components/Home/Home.tsx`

## 背景

このアプリは全データを端末内に置く。試合履歴（`minibasket-game-history`）は試合を録るたびに増え、**上限も、上限が近いことの知らせも無い**。

サイズは既に実測されており、`dataBackup.ts:483` にこう残っている。

> 実測（記録150件・12人×2チーム・日本語名の1試合）:
>   localStorage 上   52.9KB / 試合
>   localStorage 5MB の上限に達するのは約95〜99試合

週末に2試合、年30試合なら3シーズン強で到達する。遠い話ではない。

到達したときに何が起きるかは、既に手当てされている。試合終了時の履歴保存は成否を見て分岐し（`App.tsx` の保存経路）、失敗すれば「端末の空き容量が足りない可能性があります」を出し、セッションを消さない。記録は失われない。

残っている穴は**時機**である。利用者がこれを知るのは、**試合が終わって保存を押した、その瞬間**になる。体育館で撤収しながらバックアップを書き出して古い試合を選んで消す、というのは無理がある。埋まりつつあることは、もっと前に伝わっていなければならない。

## スコープ

### やること

- localStorage の使用量を測る純関数を用意する
- 8割を超えているあいだ、ホームに帯を出す

### やらないこと（YAGNI・今回のスコープ外）

- **新しい削除手段を作らない。** 履歴の1件削除（`History`）と全体バックアップの書き出し（設定 → データ管理）が既にある。まとめて消す導線は、「書き出し済みか」を確かめる設計が別途必要になり、記録を預かるアプリで一番事故になりやすいところでもある。知らせれば利用者が自分で選べる。
- **自動削除は一切しない。** 記録アプリが黙って記録を捨てることは無い。
- **IndexedDB（ミラーバックアップ）は数えない。** 別枠であり、`mirrorBackupRetention` が独自に世代を抑えている。
- **段階を分けない。** しきい値はひとつ（8割）。

## なぜ `navigator.storage.estimate()` を使わないか

あれが返すのは IndexedDB・Cache・localStorage をまとめたオリジン全体の枠で、実装によっては数百MB〜GB になる。localStorage の 5MB はそれとは**別に効く独立した壁**である。ミラーバックアップが何十MBあっても localStorage の残りには関係しない。逆に `estimate()` が「まだ 1% しか使っていない」と言っているその横で、localStorage は満杯になり得る。使えない。

自前で数えるしかない。

## 計測

`src/utils/storageUsage.ts` を新設する。

```ts
/**
 * localStorage の上限（文字数）。
 *
 * Chrome / Firefox / Safari はいずれもオリジンあたり約 5MiB を
 * UTF-16 の文字数で数える。バイト換算より端末差が出にくい。
 */
export const LOCAL_STORAGE_LIMIT_CHARS = 5 * 1024 * 1024;

/** 帯を出し始める使用率 */
export const STORAGE_WARN_RATIO = 0.8;

export interface StorageUsage {
    /** 使用中の文字数 */
    used: number;
    /** 上限の見積り（文字数） */
    limit: number;
    /** used / limit。上限を超えていれば 1 を超える */
    ratio: number;
}

export function measureLocalStorageUsage(): StorageUsage;
export function isStorageNearlyFull(): boolean;
```

数え方は全キーの走査で、`key.length + value.length` を足す。

**このアプリ以外のキーも数える。** 壁はオリジン単位に効くので、`minibasket-` で絞ると実際より軽く見える。同じオリジンに他のものが置かれていれば、それも残量を食っている。

`localStorage` に触れない環境（プライベートモードの一部、ストレージを禁じた設定）では例外が飛び得る。捕まえて `used: 0` を返す — 測れないことを理由に帯を出すのは筋が違うし、そこで落ちるとホームが描けなくなる。

## 表示

`src/components/Home/StorageWarning.tsx` を新設し、`Home` の `InstallPrompt` と同じ位置（メニューの下）に置く。カードの作りも `InstallPrompt` に揃える。

```
⚠️ 保存領域が少なくなっています
保存領域の約82%（4.3MB / 5.0MB）を使っています。いっぱいになると、
新しい試合を保存できなくなります。バックアップを書き出したうえで、
不要な試合を試合履歴から削除してください。
```

**閉じるボタンは付けない。** `InstallPrompt` は閉じられる（`minibasket-install-guide-dismissed` に残る）が、あれは「無くても困らない案内」である。こちらは放置すると記録が保存できなくなるので、8割を切るまでは出続ける。消したければ実際にデータを減らせばよい。

**ボタンも付けない。** 「設定」も「試合履歴」もすぐ下のメニューに並んでいる。帯から重ねて出す必要はなく、「押せるものだけが角丸の箱」という既存の方針にもそのまま乗る。帯は情報表示であって、操作ではない。

表示の丸めは MB で小数第1位（`4.3MB / 5.0MB`）、使用率は整数パーセント。文字数を MB へ直すときは 1MiB = 1024×1024 文字として扱う（`LOCAL_STORAGE_LIMIT_CHARS` と同じ尺度で揃える）。

**「あと何試合」は書かない。** 判断基準を使用率に決めた以上、そこだけ 52.9KB/試合 という推定値を混ぜると、人数の少ないチームや記録の薄い試合では平気で倍ずれる。外れる数字を書くくらいなら書かない。

## 計測のタイミング

`Home` の既存方針どおり、**描画のたびに測る**。

`Home.tsx:25` は `loadMyTeams` と `getGameSessionState` について既にこう決めている。

> 描画のたびに読み直す。（中略）どちらも小さなJSONの読み出しで、ホームの再描画はまれ。

使用量の計測は数MBの文字列を実体化するので、あの2つより重い。それでもマウント時1回に絞らないのは、設定モーダルからバックアップを復元してもホームは再マウントされないためである（同じコメントがその理由を書いている）。復元でデータが増えたのに帯が出ない、という食い違いをここで作りたくない。

ホームの再描画がまれであることは変わらないので、実際に走る回数は起動と画面遷移のたびに数回である。

## テスト

### `src/utils/storageUsage.test.ts`

- 空の localStorage → `used` は 0、`ratio` は 0
- キー名も数える（`setItem('ab', 'cd')` で 4 文字）
- `minibasket-` 以外のキーも数える
- 8割の境目: 直下では `isStorageNearlyFull()` が false、ちょうど・超で true
- 上限を超えていても壊れない（`ratio` が 1 を超える）
- `localStorage` が例外を投げる環境で `used: 0` を返し、帯を出さない

### `src/components/Home/Home.storageWarning.test.tsx`

- 8割未満では帯が出ない
- 8割を超えると帯が出て、使用量（MB）と使用率（%）が読める
- 帯に閉じるボタンが無い
- 帯が出ていても、メニュー（新規試合開始・試合履歴）はいつもどおり押せる

しきい値を跨がせるには、`measureLocalStorageUsage` を差し替えるのではなく **実際に localStorage を太らせる**（`setItem` で 4.2MB 分の文字列を置く）。測る対象が localStorage そのものなので、そこを模してしまうと何も確かめたことにならない。
