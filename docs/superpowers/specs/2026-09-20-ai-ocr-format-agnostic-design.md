# AI写真読込を様式に依存しないようにする — 設計

- 日付: 2026-09-20
- ステータス: 設計承認済み（2026-09-20）
- 対象: `src/utils/imageOCR.ts`, `src/utils/playerStatsAnalysis.ts`, `src/utils/mergedPlayers.ts`,
  `src/components/OpponentManager/OpponentManager.tsx`, `src/utils/teamStorage.ts`（コメントのみ）

## 背景

AI写真読込（Gemini経路）は、様式の違うメンバー表を渡すと背番号とライセンスNo.を取り違える。
利用者からの報告は「背番号とID下3桁が区別されず、的確にデータ読み取りができない」。

### 主対象の様式は、アプリ自身が印字しているもの

年間の試合の大半は公式戦以外で、そこで受け取るのは**スコアシートのメンバー表のコピー**である。
その様式はアプリ自身が印字している（`RunningScoresheet.tsx:446-452`）。

| 列 | 見出し | 中身 | 実装 |
|---|---|---|---|
| 1 | `No.` | 通し番号 1,2,3… | `RunningScoresheet.tsx:137` の `{index + 1}` |
| 2 | `ライセンスNo.` | JBA登録番号の下3桁（3マス） | `RunningScoresheet.tsx:138` |
| 3 | `選手名` | 氏名 | |
| 4 | `No.` | **背番号** | `RunningScoresheet.tsx:146` |
| 5 | `出場時限` | ①②③④ | |
| 6 | `ファウル` | 1〜5 | |

**見出しが `No.` の列が2つあり、どちらにも「背番号」とは書かれていない。**
氏名の左右に短い数字列が3本並ぶ（通し番号・ライセンスNo.・背番号）。
通し番号は 1,2,3… と並ぶため背番号らしく見え、取り違えても一覧がもっともらしく見えて気づきにくい。

### プロンプトが主対象の様式に存在しない形式を探させている

`imageOCR.ts:239-248`:

```
  {"number": 4, "name": "田中太郎", "licenseNo": "ABC1234567"},
- licenseNoはJBA登録番号（ライセンス番号）。半角英数字で出力。画像に記載がない場合は省略可
```

10桁の英数字を例示している。しかし10桁が載るのは**公式戦のプログラムだけ**で、
それ以外の試合のメンバー表は**3桁だけ**のことが多い。年間では後者が大半。
アプリ自身も「※ライセンスNo. とは、JBA登録番号(メンバーID)の下3桁を記入してください。」と
注記している（`RunningScoresheet.tsx:571`）。

探すべき形式が実物と食い違っているので、モデルは近くの数字で代用する。

### 「省略可」と捏造指示

```
- 背番号が読み取れない場合は0
- 名前が読み取れない場合は「選手」+連番
- ...画像に記載がない場合は省略可
```

「省略**可**」は許可であって禁止ではない。出力例は2件とも `licenseNo` が埋まっている。
ID欄の無い様式では、画像内の別の数字（学年など）が `licenseNo` に流れ込む。

「読めなければ捏造しろ」という2つの指示も有害である。`0` は `isValidPlayerNumber` を通る
正規の背番号なので、見出し行・監督/コーチ/マネージャー/帯同審判の行が
「背番号0の選手」として登録され得る。

### 受け側の検証が非対称

| 取り違えの向き | 現在の挙動 | 場所 |
|---|---|---|
| メンバーID → `number` | 0〜99の範囲外なので `continue`。**その選手が黙って消える** | `imageOCR.ts:334` |
| 背番号 → `licenseNo` | 記号除去だけで素通り。`"7"` でも通る | `imageOCR.ts:340` |

### 氏名の空白が正規化されていない

公式様式の氏名は均等割付で字間に全角スペースが入る。
Tesseract経路は `normalizeOcrLine` で全角スペースを潰すが（`imageOCR.ts:59`）、
Gemini経路の氏名は `.trim()` だけである（`imageOCR.ts:339`）。前後しか削らないので字間が残る。
氏名は選手識別の最後の砦なので（後述）、ここが揺れると寄せ直しが効かない。

## 判別の基礎になる不変条件

取り違えの相手はすべて2桁以下である。

| 値 | 桁数 |
|---|---|
| 背番号 | 1〜2桁（0〜99、`00` を含む） |
| 通し番号 | 1〜2桁（1〜15） |
| 学年 | 1桁 |
| 出場時限・ファウル | 1桁 |
| **ライセンスNo.（下3桁）** | **3桁** |
| **JBA登録番号（プログラム）** | **10桁** |

**`背番号 ≤ 2桁` / `licenseNo ≥ 3桁`。重ならない。**

この規則は様式に依存しないので、プロンプトにも受け側の検証にも同じ形で書ける。
「1〜2桁の `licenseNo` は存在しない」だけで、報告された混同のほぼ全部を弾ける。

桁数で切れない唯一の組み合わせは**背番号 vs 通し番号**（どちらも1〜2桁）。
これには別の手掛かりを2つ併記する。

- **位置**: 公式様式では選手名より**右**の `No.` が背番号、左が通し番号
- **連番判定**: 欠番なしで 1,2,3,…,n と並ぶ列は通し番号。背番号は普通そうならない

片方しか使えない様式でも当たるよう、両方を書く。

## 対象様式と優先順位

| 優先 | 様式 | 扱い |
|---|---|---|
| 主 | 公式様式メンバー表のコピー（ライセンスNo. = 3桁） | 列を名指しで教える |
| 主 | ID欄の無い表 | `licenseNo` は `null` を強制 |
| 副 | 公式戦プログラム（10桁英数字） | 10桁も有効値として受ける |
| 稀 | 1枚に複数チーム | 検出したらエラーで突き返す |

大会プログラムから相手チームを登録するのは稀なので、複数チームの選択UIは作らない。

## 変更内容

### 1. プロンプト再設計（`imageOCR.ts:238-250` を全面差し替え）

- 冒頭の「この画像は…選手名簿（メンバー表）です」という**1枚＝1チームの断定をやめる**
- **背番号の規則**
  - 0〜99（`00` を含む）
  - 見出しが `No.` の列が2つある様式では、**選手名より右の `No.`** が背番号
  - 欠番なしで 1,2,3,…と並ぶ列は通し番号であり、背番号ではない
- **licenseNo の規則**
  - 見出しが `ライセンスNo.` / `JBA登録番号` / `メンバーID` / `会員番号` の列**のみ**から取る
  - 3桁の数字、または10桁の英数字
  - **1〜2桁にはならない**
  - 該当する列が無ければ `null`（「省略可」を廃止）
- **名指しの禁止**: 通し番号・学年・学校・身長・年齢・出場時限・ファウル数を `licenseNo` に入れない
- **捏造指示の全廃**: 「背番号が読み取れない場合は0」「名前が読み取れない場合は選手+連番」を削除し、
  **読み取れない行は出力しない**に置き換える
- **除外行**: 監督・コーチ・Aコーチ・マネージャー・帯同審判・見出し行・空行
- 氏名は字間の空白を詰めて返す
- 複数チームが写っている場合は `teams` に複数返す

### 2. 構造化出力

`generationConfig`（`imageOCR.ts:276`）に追加する。

```ts
generationConfig: {
    temperature: 0.1,
    maxOutputTokens: 2048,
    responseMimeType: 'application/json',
    responseSchema: {
        type: 'object',
        properties: {
            teams: {
                type: 'array',
                items: {
                    type: 'object',
                    properties: {
                        teamName: { type: 'string', nullable: true },
                        players: {
                            type: 'array',
                            items: {
                                type: 'object',
                                properties: {
                                    number: { type: 'integer' },
                                    name: { type: 'string' },
                                    licenseNo: { type: 'string', nullable: true },
                                },
                                required: ['number', 'name'],
                            },
                        },
                    },
                    required: ['players'],
                },
            },
        },
        required: ['teams'],
    },
}
```

`responseSchema` で型が保証されるので、`textResponse.match(/\[[\s\S]*\]/)` による
JSON抜き出し（`imageOCR.ts:307`）は不要になる。

`FALLBACK_MODELS`（`geminiClient.ts:14`）は全てGemini 2.5系以降なので `responseSchema` に対応する。
未対応モデルが混じった場合に備え、スキーマ由来の400は既存の**次モデルへ送る**経路で扱う
（`GeminiFatalError` にはしない）。

### 3. 受け側の検証（`imageOCR.ts:330-345`）

- `licenseNo` が英数字1〜2桁なら**破棄**（誤読確定）。3桁以上はそのまま通す
  （4〜9桁や11桁以上は未知の様式があり得るので殺さない）
- `teams` の件数による分岐を明示する

  | `teams` の件数 | 扱い |
  |---|---|
  | 0件、または全チームの `players` が空 | 既存の「有効な選手を取り出せませんでした」で例外 → Tesseractへフォールバック |
  | 1件 | そのチームの `players` を使う |
  | 2件以上 | 「複数チームが写っています。1チーム分に切って撮り直してください」で失敗させる |

  2件以上のときは**Tesseractへフォールバックさせない**。撮り方の問題なので、
  端末内OCRに回しても同じ写真から正しい1チームは出てこない。それどころか
  `parseOcrText` は行単位で拾うので4チーム分の選手が混ざった名簿がもっともらしく返り、
  利用者が誤りに気づけない。

  ただし既存の `GeminiFatalError` ではこれを表現できない。あれは
  「モデルを変えても同じ」を意味するだけで、`recognizePlayerList` の `catch` は
  種類を問わずTesseractへ回す（`imageOCR.ts:390-396`）。
  **フォールバックを止める新しい例外型を1つ追加する**（`ImageFormatError` など）。
  `recognizePlayerList` はこれだけを特別扱いし、Tesseractを試さずに
  `{ success: false, error: <案内文> }` を返す。

- **後方互換**: 応答が `teams` を持たない素の配列だった場合（旧形式、または `responseSchema` 非対応モデル）は、
  1チーム分の `players` とみなして受ける。現在の `if (!Array.isArray(parsed))` を置き換える際に消さない
- **背番号が範囲外で捨てた行を数えて報告する**。現在は `imageOCR.ts:334` で黙って `continue` しており、
  選手が消えたことが誰にも分からない。`ImageOCRResult` に件数を持たせ、
  `OpponentManager` の `overflowCount` と同じ形で画面に出す

### 4. 選手識別の正規化（`playerStatsAnalysis.ts:140`）

`generatePlayerKey` の**比較時のみ** `licenseNo` を下3桁に揃える。保存は読み取ったまま。
印字は `licenseDigits()` が既に `slice(-3)` しているので影響しない（`licenseDigits.ts:17`）。

```ts
export function generatePlayerKey(name: string, licenseNo?: string): string {
    const trimmed = (licenseNo ?? '').trim();
    if (trimmed) return `${name}_${trimmed.slice(-3)}`;
    return name;
}
```

`slice(-3)` は3文字未満の文字列をそのまま返すので、1〜2桁が残っている古い保存データも壊さない
（新規の読み取りでは1〜2桁は §3 で破棄される）。

#### 保存済みの手動統合を壊さないこと

`generatePlayerKey` の出力は**そのまま保存されている**。手動統合（`mergedPlayers`）は
`MergeMap = Record<string, string>` を識別キーで引く形で `localStorage` に持ち、
バックアップにも入る（`mergedPlayers.ts:17`, `dataBackup.ts:118,131,1349`）。

キーの作り方を変えると、`田中太郎_ABC1234567` で保存された統合が新しいキー
`田中太郎_567` と一致せず、**利用者が手で行った統合が黙って効かなくなる**。

この変更で最も壊れやすいのはここなので、読み込み時に矯正する。
`loadMergedPlayers` / `loadAllMergedPlayers`（`mergedPlayers.ts:51,55`）で、
読み出した `MergeMap` のキーと値の両方を新しい正規化へ通す。保存形式は変えない。
アプリの他の保存領域と同じ「読み込み時に矯正する」約束にそろえる。

矯正の結果2つのキーが1つに畳まれた場合（`..._ABC1234567` と `..._567` の両方に
統合先が記録されていた場合）は、**先に現れたほうを残す**。どちらも同一人物を指すので
どちらを採っても同じ人に寄るが、挙動を決めておかないと読み込むたびに結果が変わる。

Gemini経路の氏名にも空白正規化を通し、Tesseract経路（`normalizeOcrLine`）と揃える。

#### なぜ比較時に揃えるか

ライセンスNo.が動くとキーが割れることは既に想定済みで、`buildIdentityAliases`（`playerStatsAnalysis.ts:184`）が
**氏名で名簿を引いて寄せ直している**。10桁と3桁の割れも、名簿に同名が1人なら自動的に治る。
したがって「全部が繋がらなくなる」わけではない。残る穴は3つだけである。

1. **同姓同名が名簿に2人** — `claimed.length !== 1` で意図的に寄せない（`playerStatsAnalysis.ts:199`）。
   ライセンスNo.で区別しているはずの2人が、10桁/3桁の違いで割れる
2. **退団選手** — 名簿に無いので寄せ先が無く、割れたまま残る
3. **氏名が一致しない場合** — 寄せる手掛かりが氏名なので、氏名が揺れると何も効かない

下3桁に揃えると1と2が別人化しない。同姓同名を区別したいケースは、下3桁が違えば区別され続ける。
3は氏名の空白正規化が受け持つ。

### 5. コメントの不一致を直す

`teamStorage.ts:41` は「JBA登録番号・半角英数10桁」、`game.ts:78` は「JBA登録番号の下3桁」と
食い違っている。実態は**両方あり得る**（公式戦プログラム = 10桁、それ以外 = 3桁）ので、
両方を受ける旨に書き換える。桁数の統一はしない（印字が `slice(-3)` する以上、統一する利益がない）。

## テスト

- `parseOcrText` の既存テストは変更しない（Tesseract経路は触らない）
- Gemini応答の検証に対する新規テスト
  - `licenseNo` が1〜2桁なら破棄される
  - `licenseNo` が3桁・10桁なら保持される
  - `teams` が2件ならエラーになる
  - 背番号が範囲外の行を捨てた件数が返る
  - 氏名の字間の空白が詰まる
- `generatePlayerKey` のテスト
  - `("田中太郎", "ABC1234567")` と `("田中太郎", "567")` が同じキーになる
  - `("田中太郎", "123")` と `("田中太郎", "567")` は別キーのまま
  - `licenseNo` 未設定なら氏名のみ（既存の挙動）
- `mergedPlayers` のテスト
  - 旧キー（10桁）で保存された統合が、読み込み後に新キーで引けること
  - 旧キーと新キーの両方が保存されていても、読み込みのたびに同じ結果になること
- `src/utils/playerStatsAnalysis.*.test.ts` と `dataBackup` の既存テストが通ること
  （識別キーの変更が波及する範囲の回帰確認）
- 既存の `imageOCR.*.test.ts`（retry / fallback / aiGate）が通ること

## やらないこと

- **複数チームの選択UI** — 稀なのでエラーで突き返すだけにする
- **Gemini生応答の画面表示** — 診断には有用だが、今回は見送る
- **`licenseNo` の桁数統一** — 印字が `slice(-3)` する以上、利益がない
- **Tesseract経路の変更** — 今回の報告はGemini経路のもの

## 未解決の限界

- 背番号 vs 通し番号は、位置と連番判定という**経験則**で切り分ける。
  両方が使えない様式（通し番号が右にあり、かつ背番号も連番）では当たらない
- 裏写り・湾曲・見切れのある写真は、どの規則でも読み違える。
  撮り直しを促す以上のことはしない
