# 試合終了時に、追加した相手選手を名簿へ取り込む — 設計

- 日付: 2026-09-07
- ステータス: 設計承認済み（2026-09-07）
- 対象: `src/utils/`（新規1ファイル）, `src/App.tsx`, `src/components/Modal/ConfirmModal.tsx`

## 背景

v1.7.0 で、スタメン選択画面と交代モーダルから試合中に選手を追加できるようになった。しかし**追加した選手はその試合にしか残らない**。

実測で確認した現状（本番 v1.7.0）:

| 保存先 | 追加した `#13 遅刻太郎` |
|---|---|
| 進行中の試合（`minibasket-game-session`） | 居る |
| 試合履歴（`saveGameResult`） | 居る（チームまるごと保存される） |
| チーム名簿（`minibasket-opponent-teams` ほか） | **居ない** |

名簿へ書き込むのは「マイチーム管理・対戦チーム管理・対戦チーム選択・データインポート」の4か所だけで、試合中の `ADD_PLAYER_TO_TEAM` はどこからも名簿に書き戻していない。対戦チームの保存（`saveRecentOpponent`、`App.tsx:313`）も**試合開始時に一度だけ**、設定ウィザードで選んだ時点の名簿を保存している。

結果として、遅れて来た選手は次の試合でまた手で登録し直すことになる。

## スコープ

### やること

- 試合終了・保存の直後に、**相手チーム**へ追加された選手を名簿に取り込むか尋ねる
- 取り込むのは**背番号と名前だけ**
- 相手チームが名前で一意に特定できるときだけ尋ねる

### やらないこと（YAGNI・今回のスコープ外）

- **マイチームの取り込み**。自チームの名簿はマイチーム管理で整備されており、書き戻しの実益が薄い
- 未登録の相手チームを新規登録する提案。練習試合の一度限りの相手が名簿に溜まる
- 保存先をユーザーに選ばせるUI。特定できないときは尋ねない方針にしたため不要
- コートネーム・ライセンスNo. の取り込み。試合中の追加では入力手段が無い
- `Team.savedTeamId` を相手チームにも入れること（後述の理由により不可）

## 調査で分かった制約

### 相手チームは名前でしか特定できない

`Team.savedTeamId` は**マイチームにしか入らない**（`matchTeams.ts` の `buildMatchTeams`）。`types/game.ts:84-91` に理由が書かれている:

> 相手チーム側にはあえて入れない。自分の別チームを「相手チーム」として登録して記録した練習試合（6年 vs 5年）は、いま 5年 側の名前照合で拾えている。相手側に相手レコードの id が入ると id 照合が外れ、その試合が 5年 の分析から消える。

過去に実際に起きた不具合なので、**ここは触らない**。

`setupData`（相手の `SavedTeam` を持つ）は `handleGameSetupComplete` のローカル引数で、App の state にも中断セッション（`GameSession` は `game` / `gameName` / `date` / `savedAt` のみ）にも残らない。再開後は復元できない。

したがって**名前照合が唯一の手段**であり、名前照合が曖昧なら尋ねない。

### 保存先は2つある

| キー | 何 | いつ書かれるか |
|---|---|---|
| `minibasket-opponent-teams` | 対戦チーム管理の登録一覧 | 対戦チーム管理での保存、または対戦チーム選択で「登録する」を選んだとき |
| `minibasket-recent-opponents` | 直近の対戦履歴 | 相手を選ぶたび・試合開始時 |

試合設定は**どちらからも選べる**（`OpponentSelect` が両方を並べる）。片方だけ更新すると、次の試合でもう片方から選んだときに古い名簿が出てきて「登録したのに反映されない」ように見える。

## 設計判断（ユーザー合意事項）

| 論点 | 決定 | 理由 |
|---|---|---|
| 対象チーム | **相手チームだけ** | 自チームの名簿は整備済み。追加が溜まるのは相手側 |
| 取り込む内容 | **背番号と名前だけ** | 試合中の追加ではそれ以外を入力する手段が無い |
| 特定方法 | 名前照合 | 相手には `savedTeamId` が無く、入れると別の不具合が復活する |
| 特定できないとき | **尋ねない** | 違うチームの名簿に黙って書き込む事故を起こさない |
| 更新先 | **名前が一致した保存先すべて** | 片方だけだと、もう片方から選んだ次の試合で反映されて見えない |
| 15人超過 | 止めない。ダイアログに添える | 退場者・スコアシートあふれと同じ「止めずに伝える」方針 |

## いつ尋ねるか

`handleGameFinished`（`App.tsx:856`）の中、**履歴への保存が成功した後**（`if (!saved) return;` の後）。保存に失敗したときは尋ねない——既にエラー通知が出ている場面で確認を重ねない。

既存のバックアップ督促（`isBackupDue()` → `setShowBackupPrompt(true)`）が `setScreen('home')` の後にプロンプトを出す前例があるので、同じくホームへ遷移してからダイアログを出す。

**2つのプロンプトが重ならないようにする。** バックアップ督促の判定を関数に切り出し、

- 取り込みを尋ねないとき: これまでどおりその場で督促を判定する
- 尋ねるとき: 取り込みダイアログを閉じた後（登録した／しなかったのどちらでも）に督促を判定する

## 追加された選手の見つけ方

追加を追跡する状態は増やさない。**試合終了時に突き合わせる。**

相手チームは `isMyTeam === false` の側（`state.teamA` / `state.teamB`）。どちらも `isMyTeam` が偽で判別できない場合は何もしない。

保存済みの名簿と試合中の名簿を**背番号で**突き合わせ、試合側にしか無い背番号を「この試合で追加された選手」とする。背番号は選手の識別子であり、重複しないことが登録時に保証されている。

## 新しいモジュール

`src/utils/opponentRosterWriteback.ts`。保存は行わない純粋な関数にして、`App.tsx` は「尋ねて、確定したら保存する」だけにする。

```ts
export interface OpponentWriteback {
    /** ダイアログに出すチーム名 */
    teamName: string;
    /** 取り込む選手（背番号順） */
    added: SavedPlayer[];
    /** saveOpponent へそのまま渡す。名前が一致しなければ空 */
    updatedRegistry: SavedTeam[];
    /** saveRecentOpponent へそのまま渡す。名前が一致しなければ空 */
    updatedRecent: SavedTeam[];
    /** 登録後の人数（最大のもの）。15人超過の案内に使う */
    resultCount: number;
}

/**
 * 取り込みの計画を立てる。尋ねる必要が無ければ null。
 *
 * null を返すのは次のいずれか:
 * - 相手チームを判別できない
 * - 追加された選手がいない
 * - どちらかの保存先で同名が2件以上見つかった（曖昧）
 * - どちらの保存先にも見つからなかった
 */
export function planOpponentWriteback(
    teamA: Team,
    teamB: Team,
    registry: SavedTeam[],
    recent: SavedTeam[],
): OpponentWriteback | null;
```

追加する `SavedPlayer` は `{ number, name, isCaptain: false }`。名前は試合中に付いたものをそのまま持っていく（入力した名前、または `選手13` の自動命名）。直したければ対戦チーム管理で編集できる。

更新後の `players` は `sortPlayersByNumber` で背番号順に並べ直す。名簿の並びは全体でこの順序に揃えてある。

**返す `SavedTeam` は元の `id` をそのまま保つ。** `saveOpponent` は `id` で既存レコードを探して差し替え、見つからなければ追加する（`teamStorage.ts:169-179`）。`saveRecentOpponent` も `id` で既存を除いてから先頭に積む。`id` を保っていれば新しいレコードが増えることはない。

## 確認ダイアログ

既存の `ConfirmModal` を使う。

- title: `相手チームの名簿に登録しますか？`
- message: `この試合で追加した #13 遅刻太郎、#14 選手14 を「〇〇ミニバス」の名簿に登録します。次の試合から選べるようになります。`
- note（15人を超えるときだけ）: `登録すると16人になります。対戦チーム管理の上限は15人です。`
- confirmLabel: `登録する` / cancelLabel: `登録しない`

チーム名を message に入れるのは、**どの名簿に入るかを見てから決められるようにする**ため。名前照合で選んでいる以上、利用者がここで気づけることが最後の砦になる。

### `ConfirmModal` に確認ボタンの色を足す

`ConfirmModal` の実行ボタンは `btn-danger`（赤）で固定されている。取り返しのつかない削除のための作りなので当然だが、「登録する」を赤で出すと危険な操作に見える。

任意の prop を1つ足す:

```ts
/** 実行側の見た目（既定: danger）。破壊的でない確認に primary を使う */
confirmVariant?: 'danger' | 'primary';
```

既定を `danger` にするので、**既存の呼び出し側は一切変わらない**。

## テスト

### `planOpponentWriteback`（新規 `opponentRosterWriteback.test.ts`）

- 追加された選手がいなければ null
- 相手チームを判別できなければ（両方 `isMyTeam` が偽でない）null
- 登録一覧で同名が2件見つかったら null（曖昧）
- 直近履歴で同名が2件見つかったら null（曖昧）
- どちらにも見つからなければ null
- 登録一覧だけに一致 → `updatedRegistry` にだけ入る
- 直近履歴だけに一致 → `updatedRecent` にだけ入る
- 両方に一致 → 両方に入る
- 追加された選手が背番号順に並ぶこと
- 更新後の `players` が背番号順に並ぶこと（若い番号を足したら先頭に来る）
- 取り込むのは `number` と `name` だけで、`isCaptain` が false になること
- 元の `SavedTeam` を書き換えないこと（新しいオブジェクトを返す）
- `resultCount` が登録後の人数になること

### `ConfirmModal`（既存テストに追加）

- 既定では実行ボタンが `btn-danger` のままであること（既存の呼び出し側が変わらない証拠）
- `confirmVariant="primary"` で `btn-primary` になること

### App 統合（新規 `src/App.opponentRosterWriteback.test.tsx`）

- 試合中に相手チームへ選手を追加して試合を終えると、確認ダイアログが出ること
- 「登録する」で `minibasket-opponent-teams` に追加されること
- 「登録しない」で名簿が変わらないこと
- 追加していなければダイアログが出ないこと
- 保存に失敗したときはダイアログが出ないこと
- ダイアログを閉じた後にバックアップ督促の判定が走ること（2つが重ならない）

## 想定される失敗と、その扱い

| 起きること | 扱い |
|---|---|
| 相手チームが改名されていて見つからない | 尋ねない。従来どおり対戦チーム管理から手で登録する |
| 同名の相手チームが2件ある | 尋ねない。どちらに入れるべきか決められないため |
| 未登録の相手（その日限りの練習試合） | 尋ねない。名簿に一度限りの相手が溜まらない |
| 登録すると15人を超える | 止めない。ダイアログに人数を添えて判断してもらう |
| 「登録する」を押したが保存に失敗した（容量超過など） | 検出しない。`saveOpponent` / `saveRecentOpponent` は `void` を返す作りで、アプリ全体がそう使っている。直前に成功した試合履歴の保存に比べて書き込み量は桁違いに小さく、ここだけ失敗する状況は考えにくい。試合の記録そのものは既に履歴へ保存済みなので失われない |
| 自分の別チームを相手として登録した練習試合 | 相手側に `savedTeamId` を入れない現状を維持するので、選手スタッツ分析の名前照合は壊れない |
